# M12 — Kairos in the Master's own browser

Implementation spec. Read `CLAUDE.md` first.

**Status (2026-10-27):** on `m12/browser` (stacked after `m10/persona`). The product owner asked
for *"Kairos rules for clicks and purchases first"*, accepted the plan, and chose to keep
Hermes's Browser Use mode (§2). **Steps 2–4, the rules, are built**; Step 5, the profile switch,
is left for later; D-027 stays Proposed. Checks marked **(on the PC)** are in `docs/TESTING.md`.

## 1. Goal and scope

Kairos can already drive a browser through Hermes. The goal is for it to act **as the Master**
on the sites they are signed in to (mail, shops, accounts), and to **ask first** before anything
with consequences: buying, paying, sending, posting, deleting, confirming.

The order is the product owner's: **the rules first** (they guard today's fresh browser too),
then the profile switch.

Out of scope: driving the Master's *open* browser window (`browser.extension_control`,
`/browser connect`), Hermes's desktop control (`computer_use`, off), cloud browsers.

## 2. What Hermes does (read in Hermes 0.22.5's code and seen live, 2026-10-27)

- **Hermes's browser runs in "Browser Use" mode by default.** With `browser.backend` unset and
  the browser-harness package present, one tool, `browser_exec`, replaces all the others
  (`browser_navigate`, `browser_click`, …): asked for `browser_navigate`, Hermes answered
  *"'browser_navigate' is not available in this execution context"*. `browser_vault` stays.
  `browser.backend: off` would bring the built-in tools back; the product owner chose to keep
  Browser Use (2026-10-27), so Hermes's configuration is unchanged.
- **A `browser_exec` call is a Python script** run against the browser, with helpers. Seen live on
  httpbin's demo order form: `goto_url(...)`, `wait_for_load()`, `page_info()`, `js("""…""")`.
  The helpers that act on a page: `click_at_xy(x, y)` (screen coordinates, no label),
  `type_text`, `fill_input(selector, text)`, `press_key`, `dispatch_key`, `upload_file`, `js(...)`
  (any JavaScript: `.click()`, `.submit()`, setting `.value`, reading `document.cookie`), and
  `cdp(...)` (raw DevTools commands). **A click carries no button label Kairos could judge.**
- **Real-profile mode** (`browser.use_real_profile: true`, default off, read on every call) works
  in both modes. Hermes then:
  - finds the default browser: on this PC **Brave** (`BraveHTML`), which it supports;
  - copies the active profile's `Local State`, `Cookies`, `Login Data`, `Login Data For
    Account`, `Web Data` (saved passwords and autofill, which can include cards) and
    `Preferences` into a Hermes-owned folder with owner-only permissions;
  - starts the real `brave.exe` on that copy; the Master's own Brave is never touched;
  - when the switch is turned off, **deletes the copies**.
- **On Windows the first copy needs Brave closed** (a running Brave locks its cookie database).
  While Brave is open, Hermes reuses the last complete copy; closing Brave lets the next task
  refresh it. With no copy yet and Brave open, Hermes offers `hermes browser close-profile`,
  which quits Brave: Kairos must ask.

## 3. Decisions

- **The rules are built for Browser Use mode** (the product owner, 2026-10-27): every
  `browser_exec` script that clicks, types, presses keys, submits, uploads, sends raw browser
  commands or reads cookies and site storage asks; reading a page doesn't. Kairos can't tell a
  purchase from a page turn in a script, so it asks for both.
- **D-027 — Kairos may use a copy of the Master's Brave profile, behind the Kairos rules —
  Proposed**, for Step 5. Changes Hermes's configuration (`browser.use_real_profile: true`,
  `browser.restrict_evaluate: true`), with a backup as for holographic (D-026). What it means:
  Hermes's folder holds a copy of the Master's cookies and saved passwords; pages Kairos reads go
  to the model provider; a page can carry instructions aimed at the model, and the rules are the
  backstop.
- **No new dependency.**

## 4. The rules (built)

Four rules in `policy.default.json` (and `NEWER_STARTER_RULES`, so the Rules page offers them to
an existing rules file). They read `browser_exec` code like a command (M2), so no new match kind
was needed.

| Rule | Tool | Matches | Decision |
|---|---|---|---|
| `browser-settings-pages` | `browser_exec` | opening `brave://`, `chrome://`, `edge://`, `file:`, `view-source:`, `devtools:` or `about:` (not `about:blank`) pages, by `goto_url`, `new_tab` or `location =` | deny |
| `browser-no-card-numbers` | `browser_exec` | typing 13–19 digits (a card number) with `type_text` / `fill_input` / `dispatch_key` or `.value =`; `fill_input` into a field named password, passcode, CVC / CVV, card number, IBAN, mot de passe, كلمة المرور | deny, with a note to use the vault |
| `browser-page-actions` | `browser_exec` | `click_at_xy`, `click`, `type_text`, `fill_input`, `press_key`, `dispatch_key`, `upload_file`, `cdp`, `_send`; in page scripts `.click()`, `.submit()`, `requestSubmit`, `dispatchEvent`, `execCommand`, setting `.value` / `.checked` / `innerHTML`…, `document.cookie`, `localStorage`, `sessionStorage`, `indexedDB`, `fetch`, `sendBeacon`, `XMLHttpRequest`, `WebSocket` | ask |
| `browser-vault-fill` | `browser_vault` | `fill` (a saved password or card) and `save_login` | ask |

The two denials sit before `browser-code-system-access` (first match wins), the two asks after it.

**The approval card says what the script will do, in words**, above the rule and the whole
script (M1 §9 rule 3: what runs is always shown): *"It will type «Test» into
input[name="custname"]; click an element by script, on httpbin.org."* The plugin reads the
script's steps in order (open, click at, type into, press, upload, submit a form by script, read
cookies or site storage, send a raw browser command…), hides what is typed into secret-looking
fields, and remembers per conversation which site the browser was sent to. The words travel on
a last `Will:` line of the plugin's approval message; `turn.ts` reads it.
