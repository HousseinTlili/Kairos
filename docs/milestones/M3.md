# M3 — System dashboard and PC control

Implementation spec. Read `CLAUDE.md`, then `docs/ARCHITECTURE.md` §3.2, `docs/milestones/M2.md`
§4–§6 and decisions D-012 to D-014, before starting. Work through the steps in order; every step
ends with a check.

**[observed]** means seen on the real Hermes 0.22.5 or on the product owner's PC; **[source]**
means read in Hermes's source at tag `rc.1-v0.22.5` (commit `7c0905a0`) and not yet seen live.

**How M3 was built.** Steps 2–7 were written in a Linux cloud session with no Windows, no Hermes
and no display (2026-10-25). The checks that can run there (Rust unit tests, TS tests, plugin unit
tests, lint) were run there; every check that needs Windows, Hermes or the product owner's eyes is
marked **(on the PC)** and is run by the product owner before Step 8. Windows-only code is behind
`cfg(windows)` (Rust) or `sys.platform == "win32"` (Python) so the rest stays testable.

---

## 1. Goal and scope

Kairos starts acting like the assistant on the desk: it shows how the PC is doing without asking a
model, opens and closes apps through narrow tools that the M2 rules govern, warns about a low
battery, a full disk or a runaway process, and is already running when the user logs in.

**In scope**
- **System page** (native, no AI, D-012): CPU total and per core, RAM, disks (usage, free space,
  read/write speed per drive), GPU via `nvidia-smi`, network up/down, Wi-Fi network and signal,
  battery (level, charging, time left, wear), uptime, top processes by CPU and by RAM, and an
  on-demand internet speed test.
- **PC control tools** in the Kairos plugin (D-014): `list_running_apps`, `open_app`, `close_app`.
- **Proactive alerts**: low battery, a nearly full disk, a process hogging the CPU; "Close it?"
  goes through Hermes, so the `close-apps` rule asks first.
- **Starts with Windows** (D-013): Kairos in the tray and registered to start at login, a single
  instance, and Hermes's own login start (`hermes gateway install`). Kairos notices startup, resume
  from sleep and unlock, and records them for M5's welcome-back briefing.

**Out of scope:** window focus, volume, brightness, media keys, lock and sleep tools (listed in the
roadmap as "later"; each needs its own rule, so they get their own step in a later milestone),
the briefing itself (M5), notifications from other apps (M4), quiet hours (M5).

## 2. How it fits together

```
Kairos app (Tauri)                                   Hermes gateway process
──────────────────                                   ─────────────────────────────────
system/ monitor thread ── sysinfo, battery,          kairos plugin
   │                     nvidia-smi, netsh           ├ pre_tool_call (M2 rules)   ◄── every call,
   ├─► "system-snapshot" event ─► System page        │                               PC tools too
   └─► alerts ─► Windows toast + banner              ├ list_running_apps ┐
                   └ "Close it?" ─► POST /v1/runs ─► ├ open_app          ├ pctools.py (ctypes,
presence thread ── resume, unlock ─► kairos.db       └ close_app         ┘  Get-StartApps)
tray, autostart, single instance
```

- The **system readings never go through Hermes**. The model only sees them in M5 (briefing) or
  when a later tool asks for them.
- The **PC tools run inside Hermes**, so every call is checked by the M2 rules, recorded in
  `audit.db`, and shown on the chat's tool rows like any other tool.
- "Close it?" on a CPU alert does **not** close anything itself: it sends a request to Hermes,
  which calls `close_app`, which the `close-apps` rule turns into an approval card.

## 3. Decisions

- **D-013 and D-014** were accepted by the product owner on 2026-10-25 with this spec.
- **D-017 — The speed test uses Cloudflare's public speed endpoints, only when asked.** Latency,
  download and upload are measured against `speed.cloudflare.com` (`/__down`, `/__up`), only when
  the user presses "Run speed test". No account, no key, no new dependency (reqwest is already
  there). It sends the PC's IP address to Cloudflare, as any website visit does; nothing else.

## 5. System readings

### 5.1 The snapshot

A background thread owns one `sysinfo::System` and samples every **2 s while the System page is
visible**, every **15 s otherwise** (alerts still need readings when the window is in the tray).
Each sample becomes a `SystemSnapshot`, sent to the UI as the `system-snapshot` event and kept as
the latest for `system_snapshot` (the command the page calls when it opens).

| Field | Source | Notes |
|---|---|---|
| `cpu.total`, `cpu.per_core[]`, `cpu.name`, `cpu.frequency_mhz` | sysinfo | Percent. First sample after start reads 0; the page shows "—" until the second |
| `memory.used/total`, `swap.used/total` | sysinfo | Bytes |
| `disks[]`: `mount`, `name`, `kind` (SSD/HDD), `total`, `available`, `read_per_s`, `write_per_s` | sysinfo `Disk::usage()` | Rates = bytes since the last refresh ÷ seconds elapsed. Removable drives included |
| `network`: `down_per_s`, `up_per_s` | sysinfo `Networks` | Sum over interfaces, loopback excluded |
| `wifi`: `ssid`, `signal_percent` | `netsh wlan show interfaces` | Every 10 s at most. `null` when there is no Wi-Fi interface or it isn't connected |
| `gpus[]`: `name`, `load_percent`, `memory_used/total`, `temperature_c` | `nvidia-smi --query-gpu=name,utilization.gpu,memory.used,memory.total,temperature.gpu --format=csv,noheader,nounits` | `[]` without an NVIDIA GPU or driver; other GPUs are a later step |
| `battery`: `percent`, `state` (charging/discharging/full/unknown), `time_to_empty_s`, `time_to_full_s`, `health_percent` | starship-battery | `null` on a desktop. `health_percent` = full ÷ design capacity (wear = 100 − health) |
| `uptime_s`, `boot_time` | sysinfo | |
| `top_cpu[]`, `top_memory[]` (8 each): `name`, `count`, `cpu_percent`, `memory` | sysinfo processes | **Grouped by executable name** and summed, like Task Manager's app groups. CPU % is divided by the number of logical cores so 100 % means the whole CPU, as in Task Manager |
| `taken_at` | | Unix ms |

Console tools (`netsh`, `nvidia-smi`) are started with `CREATE_NO_WINDOW` and a 3 s timeout; a tool
that fails or times out leaves its section empty and sets `notes[]` (shown greyed on the page), it
never fails the snapshot. The parsers are pure functions tested on sample output. `netsh` output is
localised: the parser keys on `SSID` and `Signal`, which are the same words in English, French and
German, and accepts the non-breaking space French Windows puts before `%`.

### 5.2 Speed test (D-017)

`run_speed_test` (one at a time; a second call while one runs is refused): latency = median of 5
`GET /__down?bytes=0`; download = `GET /__down?bytes=25000000` timed from first to last byte;
upload = `POST /__up` with 10 MB. Result in Mbps and ms, kept in memory for the session. Each
ping has a 5 s limit and each transfer 15 s, so a test ends within about 40 s even on a bad line. Progress is sent as `speed-test` events (`latency` → `download` → `upload` →
`done` / `failed`).

### 5.3 Accuracy

Task Manager's CPU figure on Windows 10/11 is "% Processor Utility", which accounts for boost
clocks and can read higher than the classic "% Processor Time" that sysinfo reports. If Step 8
shows a gap larger than "a few percent", that is the likely reason; it is recorded, not hidden.

## 6. PC control tools (D-014)

Registered by the plugin with `ctx.register_tool(name, toolset="kairos", schema, handler)`
[source: `hermes_cli/plugins.py`]. Plugin toolsets are **on by default for every platform** unless
the user turned them off [source: `hermes_cli/tools_config.py` `_enabled_plugin_toolsets`], so the
API server sees them without a configuration change. Handlers take `(args, **kwargs)`, always return
a JSON string, and never raise [source: plugin developer guide]. Tool **code** changes need a
gateway restart (M2 §4).

On anything but Windows the tools report `{"error": "Kairos PC control works on Windows only"}`.

| Tool | Arguments | What it does |
|---|---|---|
| `list_running_apps` | none | Apps with a visible top-level window: `name` (executable), `title` (first window title, cut to 120 chars), `pid`, `windows` (count). System processes are left out. Read-only |
| `open_app` | `name` (string, required) | Finds the app in the **Start menu catalogue** (`Get-StartApps`: name and AppID of every Start-menu app, desktop and Store, cached 5 min) and starts it with `shell:AppsFolder\<AppID>`. Never takes a path, arguments or a command. Matching: exact name (case-insensitive) → unique prefix → unique substring; several matches → returns the candidates and opens nothing; no match → "not found" with up to 5 close names. If PowerShell fails, a small built-in list (Notepad, Calculator, Paint, File Explorer, Task Manager, Settings, Snipping Tool) still works |
| `close_app` | `name` (string, required: executable like `notepad` / `notepad.exe`, or a window title), `force` (bool, default false) | Resolves `name` to processes with visible windows: by executable name first, else by a window title containing the text (must resolve to one executable). **Refuses** if any target is a protected system process, even when the rules missed it (a window title can hide `explorer.exe`). Without `force`: posts `WM_CLOSE` to the app's windows and waits up to 5 s; an app that is still open is reported as "still open; it may be asking to save" (not as success). With `force`: terminates the processes. No `pid` argument, so a rule on the name always sees what will be closed |

The protected list is the same as rule `system-processes` (`explorer`, `winlogon`, `csrss`,
`lsass`, `services`, `svchost`, `smss`, `wininit`, `dwm`) plus `kairos` and Hermes's own Python
(the tool must not close Kairos or the gateway it runs in).

**Rules.** `system-processes` (deny) and `close-apps` (ask) are already in the starter rules (M2).
Two are added, in this order after them:

| id | Tools | Matches | Action | Why |
|---|---|---|---|---|
| `open-installers` | `open_app` | names containing `uninstall`, `setup`, `installer`, `install` | ask | Start-menu uninstallers and installers change the PC |
| `open-apps` | `open_app` | — | allow | D-014: "opening an allowed app runs"; the catalogue is the allow list. Shown as "allowed by open-apps" on the tool row |

**Existing rules files don't change by themselves.** The app never rewrites a valid `policy.json`;
after updating, the Rules page offers "Add the new M3 rules" when `open-installers` / `open-apps`
are missing (it inserts them after `close-apps` and validates as usual). `list_running_apps` needs no rule (read-only, inherits).

**Steering the model.** The tool descriptions say "Use this instead of terminal commands to open
or close apps"; nothing in Hermes's prompt is changed.

## 7. Alerts

Evaluated on every snapshot by a pure function `alerts::evaluate(state, snapshot) → (state, new
alerts)`. Each alert fires **once per episode** and re-arms only after the condition clears with a
margin, so a battery hovering at 19–21 % doesn't toast every 15 s.

| Alert | Fires | Re-arms | Toast text |
|---|---|---|---|
| `battery_low` | ≤ 20 % and discharging | charging, or > 25 % | "Battery at 18 % — about 40 min left." |
| `battery_critical` | ≤ 10 % and discharging | charging, or > 15 % | "Battery at 8 %. Plug in soon." |
| `disk_full` (per drive) | ≥ 90 % used, or < 5 GB free on the system drive | < 88 % and ≥ 6 GB | "Drive C: is 93 % full (12 GB free)." |
| `cpu_hog` (per executable) | one process group ≥ 80 % CPU in every sample for 60 s | < 50 % | "chrome.exe has used 85 % of the CPU for a minute. Close it?" |

`cpu_hog` never fires for protected system processes (they can't be closed) or for Kairos itself.
Alerts appear as a Windows toast **and** as a banner on the System page and above the chat, with
"Dismiss" and, for `cpu_hog`, **"Close it?"** — that starts a new conversation with the request
"Close <name>. It has been using about N % of the CPU." Hermes picks `close_app`, the `close-apps`
rule asks, and the user approves or denies on the approval card as usual. Alerts can be switched off
in Settings ▸ System (stored in `kairos.db`, table `setting`).

## 8. Starting with Windows (D-013)

- **Tray.** A tray icon with "Open Kairos", "System", "Quit". Closing the window hides it to the
  tray; "Quit" exits. Left-click opens the window.
- **Kairos at login.** `tauri-plugin-autostart` (Run key under HKCU, no admin) with the argument
  `--autostart`; launched that way, Kairos starts **hidden in the tray**. Settings ▸ Startup has the
  switch, **on by default after first launch** (D-013), and shows its current state.
- **Single instance.** Launching Kairos while it runs shows the existing window.
- **Hermes at login.** `scripts/install-gateway-autostart.ps1` asks first, then runs
  `hermes gateway install`, which creates the per-user logon Scheduled Task `Hermes_Gateway`
  (no admin, 30 s logon delay, restarts on failure) or a Startup-folder entry when Task Scheduler
  refuses [source: `hermes_cli/gateway_windows.py`]. It doesn't touch `.env` or `config.yaml`.
  Settings ▸ Startup shows whether the task or the Startup entry exists. Kairos never runs the
  command by itself.
- **Presence events.** A thread ticks every 5 s. A gap of more than 60 s in wall-clock time
  between ticks means the PC slept: `resume`. On Windows it also reads the session's lock state
  (`WTSQuerySessionInformationW`, `WTSSessionInfoEx`): locked → unlocked is `unlock`. App start is
  `startup` (with `autostart: true` when launched by the login entry). Each is written to
  `kairos.db` (`presence_event`, schema v2) and sent to the UI as `presence`. M5 builds the
  briefing on them; M3 only records and shows the last few in Settings ▸ Startup.

### `kairos.db` schema v2

```sql
PRAGMA user_version = 2;
CREATE TABLE presence_event (
  id     INTEGER PRIMARY KEY,
  at     INTEGER NOT NULL,      -- Unix seconds
  kind   TEXT NOT NULL,         -- startup | resume | unlock
  detail TEXT                   -- e.g. "autostart", or the length of the gap for resume
);
CREATE INDEX presence_event_at ON presence_event(at);
CREATE TABLE setting (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

Version 1 databases are migrated in place; the `task` table is untouched.

## 9. Steps

### Step 1 — Spec and decisions
This file; D-013 and D-014 accepted; D-017 added; ROADMAP and CLAUDE.md point at M3.
**Check:** the product owner has the spec (accepted in the 2026-10-25 conversation).

### Step 2 — System readings (Rust)
`src/system/` (`mod.rs` sampler and snapshot, `parse.rs` for `netsh` / `nvidia-smi`, `rates.rs`,
`processes.rs` grouping) and the commands `system_snapshot`, `set_system_page_visible`.
**Check:** unit tests for the parsers (English and French `netsh` samples, `nvidia-smi` with one and
two GPUs, "N/A" fields), rate maths (counter resets, zero elapsed), process grouping and CPU
normalisation; `cargo test` and clippy clean. **(On the PC)** `system_snapshot` returns plausible
figures.

### Step 3 — System page
`features/system/` (store, page, small inline-SVG sparklines for CPU, RAM and network over the last
2 minutes). A "System" entry in the sidebar above the conversations.
**Check:** TS tests for the formatting and history helpers (bytes, rates, durations, the sparkline
path); lint and `tsc` clean. **(On the PC)** the page matches Task Manager within a few percent
(§5.3).

### Step 4 — Speed test
`system/speedtest.rs`, command `run_speed_test`, `speed-test` events, a card on the System page.
**Check:** unit tests for the Mbps maths and the median. **(On the PC)** a run finishes in under
40 s with figures close to speed.cloudflare.com in the browser.

### Step 5 — PC control tools (plugin)
`plugin/kairos/pctools.py` (pure logic: catalogue matching, protected list, title resolution,
result shapes) and `plugin/kairos/winapps.py` (Windows calls through `ctypes` and `Get-StartApps`),
registered in `register(ctx)`; the two new starter rules; "Add the new M3 rules" on the Rules page.
**Check:** plugin tests with a fake Windows layer: exact / prefix / substring / ambiguous / missing
names, a window title that resolves to `explorer.exe` is refused, `force` only when asked, a still-
open app is not reported as closed, every handler returns JSON and never raises; policy tests for the
new rules (`open_app` "Notepad" → allowed by open-apps, "Uninstall Foo" → asks through open-installers).
**(On the PC, after a gateway restart)** "open Notepad" opens it with no prompt; "close Notepad"
shows an approval card from `close-apps`; "close explorer" is blocked by `system-processes`.

### Step 6 — Alerts
`system/alerts.rs`, toasts, banners, the setting, "Close it?".
**Check:** unit tests that walk each alert through fire → no repeat → clear → re-arm, the 60 s CPU
window, and the system-process exclusion. **(On the PC)** a CPU-burning test process raises the
alert; "Close it?" leads to a `close-apps` approval card.

### Step 7 — Starting with Windows
Tray, autostart, single instance, presence events, schema v2, Settings ▸ Startup,
`scripts/install-gateway-autostart.ps1`.
**Check:** unit tests for the v1 → v2 migration, the resume-gap detector and the lock-transition
detector (fed fake readings). **(On the PC)** close the window → it stays in the tray; second
launch focuses it; sleep and wake → `resume` recorded; lock and unlock → `unlock` recorded.

### Step 8 — Acceptance (product owner, on the PC)
The three ROADMAP criteria, recorded in `docs/milestones/M3-acceptance.md`:
1. The System page matches Task Manager within a few percent (CPU, RAM, disk, network, GPU).
2. "Open Notepad" runs; "close Notepad" asks first.
3. After a reboot, Kairos (in the tray) and Hermes are both running with nobody starting them.

## 10. Definition of done

- Every step check passes with recorded output, including the **(on the PC)** ones.
- Plugin tests, `cargo test`, clippy, `cargo fmt --check`, `pnpm test`, lint, `tsc` clean.

  invented (no real SSIDs or serial numbers).
- Approval mode is still `smart`.
