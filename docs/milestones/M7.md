## 1. Goal and scope

- **Isolation:** the agent's commands run inside a container (Docker Desktop with WSL2), with only
  the chosen project folders mounted, so a command that slips past a rule (M2's "rules are
  patterns, not a sandbox") can't reach the rest of the PC.
- **Models:** pick the model per conversation from what Hermes can route to, including a local
  model (Hermes manages llama.cpp itself) and the fallback chain.
- **Cost:** tokens and an estimated cost per request and per conversation, and a per-request cost
  cap that stops a run that goes over.

**Out of scope:** Kairos running its own containers (Hermes's Docker backend does it), Kairos-side
provider keys (Hermes owns them, D-006), billing reconciliation with providers.

## 2. Decisions

- **D-019 — Isolation is Hermes's Docker terminal backend, one container per conversation —
  Accepted (on the product owner's delegation, 2026-10-25; to confirm at testing).** Hermes runs
  `terminal` (and file tools through it) in Docker when `terminal.backend: docker` [source:
  configuration.md "Docker backend"]. Kairos sets it up with a script that asks first:
  `container_persistent: false` (a fresh container per conversation, removed when it ends), the
  product owner's project folders mounted (read-write) under `/workspace/projects`, nothing else
  of the PC. Network stays on (the use cases need git and package downloads). The rules still run
  first; the container is the second line.
- **D-020 — Cost is estimated from Hermes's own prices; the cap is enforced by Kairos stopping the
  run — Accepted (same delegation).** `/api/model/options` gives each provider's per-model prices
  in $ per million tokens [source: `hermes_cli/inventory.py`]; each run reports `usage` (input,
  output, cache-read tokens) and the `runtime` provider/model that actually served it, even after a
  fallback [source: api-server.md]. Kairos multiplies them, labels the result an estimate, and
  while a capped run is active polls its status; when the estimate passes the cap it calls
  `/v1/runs/{id}/stop` and says why. If Hermes only fills `usage` at the end of a run, the cap can
  only stop the *next* request of that conversation; testing records which.

## 3. Isolation

`scripts/setup-container.ps1` (asks first; `-Status`, `-Undo`):

1. Checks `docker version` answers (Docker Desktop with the WSL2 engine running).
2. Asks which project folders to mount (default: the folders in Settings ▸ Briefing ▸ Projects,
   else `%USERPROFILE%\Projects` if it exists).
3. Runs, through the Hermes CLI (never editing `config.yaml` by hand):
   `hermes config set terminal.backend docker`, `terminal.container_persistent false`,
   `terminal.docker_mount_cwd_to_workspace false`, `terminal.docker_volumes <JSON list>`.
4. `-Undo` sets `terminal.backend local` (the other keys are harmless when not on Docker).

A new starter rule keeps the agent from undoing it: **`no-sandbox-changes`** (deny) on
`hermes config set/unset/edit terminal.*` and `hermes config edit`, for `terminal`,
`execute_code` and `browser_exec`. Settings ▸ Models & sandbox shows the current backend
(`hermes config get terminal.backend`, like the approval mode in M1).

## 4. Models

- **The picker:** a model menu above the message box. Choices come from `/api/model/options`
  (providers with `slug`, `name`, `models`, `pricing`, and the current `model`/`provider`)
  [source]. "Hermes default" sends nothing, so Hermes's own choice and its fallback chain apply.
- **Per conversation:** the choice is stored in `kairos.db` (`conversation` table) and sent as
  `model` + `provider` on every `/v1/runs` request of that conversation (Hermes honours them on
  `/v1/runs` [source: api-server.md "Per-request model selection"]).
- **Local model:** Hermes's own Local Models (llama.cpp it downloads and runs) appear in the same
  list as the `llamacpp` provider once a model is downloaded in Hermes Desktop [source:
  local-models.md]; Kairos adds nothing.
- **Fallback providers:** configured in Hermes (`hermes fallback add`); Kairos shows which
  provider and model actually served each request (`runtime`), so a fallback is visible.

## 5. Cost

- **Per request:** input, output and cache-read tokens and the estimated cost, from `run.completed`
  (`usage`, `runtime`) and the served model's price. Shown under each answer ("1.2k in · 300 out ·
  ≈ $0.0021 · openrouter/…"); "free" for free models; "price unknown" when Hermes has none.
- **Per conversation:** the sum, in the chat header.
- **Cap:** Settings ▸ Models & sandbox ▸ "Stop a request that costs more than $…" (default off).

### `kairos.db` schema v4

```sql
PRAGMA user_version = 4;
CREATE TABLE conversation (
  session_id TEXT PRIMARY KEY,
  provider   TEXT,          -- null = Hermes default
  model      TEXT
);
ALTER TABLE task ADD COLUMN input_tokens INTEGER;
ALTER TABLE task ADD COLUMN output_tokens INTEGER;
ALTER TABLE task ADD COLUMN cache_read_tokens INTEGER;
ALTER TABLE task ADD COLUMN cost_usd REAL;          -- estimate; null = price unknown
ALTER TABLE task ADD COLUMN served_provider TEXT;
ALTER TABLE task ADD COLUMN served_model TEXT;
```
