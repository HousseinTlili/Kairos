## 1. Goal and scope

The product owner's first use cases (Q-2):

1. **Welcome-back briefing** (the headline feature). When the user comes back to the PC (startup,
   wake or unlock), after a configurable time away and outside quiet hours: instant facts with no
   AI, then a short AI summary with suggestions.
2. **Debug-and-fix**, 3. **Code review**, 4. **Documents to actions**: each a Hermes skill, with
   the rules that keep it in bounds.
5. **An evaluation set**: repeatable tasks with checkable outcomes, run by a script against the
   real Hermes, results stored.

**Out of scope:** calendar and email in the briefing (M6 adds them once accounts exist), voice
(M9), a scheduled morning briefing without a return to the PC (M8's scheduled jobs).

## 2. The briefing

### 2.1 When

Triggered by the M3 presence events, each now carrying how long the user was away:

| Event | Time away |
|---|---|
| `startup` | since Kairos last saw the PC in use (`last_seen`, written every minute) |
| `resume` | the sleep gap (M3) |
| `unlock` | since the session locked (the lock is now noticed too) |

The pure rule `briefing::rules::decide` briefs when **all** hold:

- briefing is on (Settings ▸ Briefing, default **on**);
- the local time is **outside quiet hours** (default 22:00–07:00; an empty range turns them off);
- **either** this is the first return of the local day **or** the user was away at least the set
  time (default **60 min**);
- no briefing in the last **10 minutes** (a wake is often followed by an unlock).

Local time comes from the app's own clock (the page reports its UTC offset to the core at startup
and every hour, so daylight-saving changes are followed without a new dependency).

### 2.2 What: instant facts, no AI

Built by `briefing::facts::build` from what Kairos already has, in this order, each only when
there is something to say:

| Fact | Source |
|---|---|
| "You were away 2 h 10 min" | the trigger |
| Battery level, charging, time left; a warning under 20 % | the latest system snapshot (M3) |
| The Wi-Fi network and signal, when on Wi-Fi | the snapshot |
| A drive over 90 % full | the snapshot |
| "5 unread notifications: Phone Link 2, Discord 3" (app names and counts, never text) | the notification store (M4) |
| "2 requests finished while you were away" / "1 request is waiting for your approval" | `kairos.db` tasks |

They appear at once as a **briefing card** above the chat and as a Windows toast ("Welcome back").
The card stays until dismissed; the latest briefing can be reopened from the sidebar.

### 2.3 Then: the AI summary

With "AI summary" on (default on), the app starts a Hermes request in a new conversation called
"Welcome back", unless a request is already running (then the card offers a button instead). The
prompt holds the facts as data (counts and names, no notification text), and asks for at most five
short lines: what needs attention first, then suggestions. The model may call
`recent_notifications` (D-018) to see what the messages say, and its own tools for the repositories
listed in Settings ▸ Briefing ("Projects": folders whose `git status` and failing tests it may
check, read-only by instruction; the existing rules still apply). Calendar and email join in M6.

## 3. The skills

Three skills in the repository, `skills/kairos/<name>/SKILL.md`, in Hermes's skill format.
`scripts/install-skills.ps1` links `%HERMES_HOME%\skills\kairos` to the repository's `skills/kairos`
folder (a directory junction, like the plugin), asking first. Hermes picks skills up on the next
conversation; each is also a slash command (`/kairos-code-review`).

| Skill | Does | Boundaries (instruction) | Boundaries (rules, enforced) |
|---|---|---|---|
| `kairos-debug-and-fix` | Reproduce an error, find the root cause, propose a fix; apply it when the user agrees; hand large changes to Claude Code or Codex | Reproduce before changing; one minimal fix; run the tests | `delegate-cli` and `delegate-to-agents` ask before any hand-off; `destructive-commands`, `git-publish` ask |
| `kairos-code-review` | Review a branch, diff or PR for bugs, security problems and missing tests | Read-only: no edits, no commits | `git-publish` asks before any `gh pr comment/review`; read-only itself is by instruction (rules are global, not per skill) |
| `kairos-documents-to-actions` | Summarise PDF, Word and Excel files (Hermes's `read_file` converts them) and extract action items | Writes only to `Documents\Kairos\output` | By instruction; writes elsewhere still go through the normal rules (`system-files`, `no-kairos-tampering`, …) |

**A new rule** guards the installed skills themselves: `kairos-skills` asks before `write_file`,
`patch` or `skill_manage` touch `**/hermes/skills/kairos/**` (the agent may otherwise rewrite its
own instructions; Hermes's `skill_manage` can edit skills wherever they live).

**Honest limit:** Kairos rules are global, not per skill. "Read-only" and "writes only to the
output folder" are instructions to the model, backed by the global rules that make the risky
actions ask (pushing, posting, deleting, delegating). That is recorded in the acceptance file.

## 4. The evaluation set

`eval/` holds 12 tasks (`eval/tasks/*.json`) and their fixtures. `eval/run.py` (Python standard
library, like the plugin; run with Hermes's own Python) sends each task to the real Hermes through
`/v1/runs`, answers approvals the way the task says (usually **deny**, to prove the ask happened
without letting anything run), waits for the end, and checks the outcome:

| Check | Meaning |
|---|---|
| `output_contains` / `output_excludes` | words that must (not) appear in the answer, case-insensitive |
| `asked` | an approval was requested (a rule or Hermes asked) |
| `not_asked` | no approval was requested |
| `files_unchanged` | the fixture files are byte-identical afterwards |
| `status` | the run ended `completed` (or the expected status) |

Tasks cover the four use cases and the rules: a planted off-by-one the review must find, a
failing test the debug skill must name, a document with three action items, a review that must
ask before posting to GitHub, a prompt injection in a fixture README, and so on.

**The key.** The runner reads the Hermes API key from Windows Credential Manager (the entry the
app uses, `hermes-api-key.kairos`) through `ctypes`, never from `.env`, and never prints it.
**Idempotency:** each task's key is written to the results file before the run is created; a rerun
of the same results file reuses it (M1 §9 rule 1).

**Results** go to `%APPDATA%\kairos\eval\<timestamp>.json` (outside the repository: answers may hold
personal paths), with a one-line summary per task printed.

## 5. Data

No schema change. Settings (`setting` table): `briefing_enabled`, `briefing_min_away_min`,
`briefing_quiet_start`, `briefing_quiet_end` (`HH:MM`), `briefing_ai_summary`,
`briefing_projects` (JSON list of folders), `last_seen`, `last_briefing` (the latest briefing as
JSON, for the sidebar).

## 6. Steps

### Step 1 — Spec
This file; ROADMAP, CLAUDE.md and `docs/TESTING.md` point at it.

### Step 2 — Time away
`presence.rs`: lock detection alongside unlock, `away_s` on each event, the `last_seen` heartbeat.
**Check:** unit tests: lock → unlock gives the time locked; startup uses `last_seen`; resume uses
the gap.

### Step 3 — Briefing rules
`briefing/rules.rs`: settings with defaults, quiet hours (including ranges over midnight), first
return of the day, minimum time away, the 10-minute guard.
**Check:** table-driven unit tests for each rule and the edges (exactly at the threshold, quiet
hours 22:00–07:00 at 06:59 and 07:00, an empty range).

### Step 4 — Briefing facts
`briefing/facts.rs`: the facts from the snapshot, notification counts and tasks.
**Check:** unit tests: each fact appears only when it has something to say; no notification text
ever appears; the order.

### Step 5 — Trigger, card, toast and settings
The presence callback runs the rules, builds the facts, stores `last_briefing`, emits `briefing`,
shows the toast. `features/briefing/` (card, prompt builder, AI summary start), Settings ▸
Briefing, a "Brief me now" button for testing.
**Check:** TS tests for the prompt (facts as data, no notification text, the five-line ask) and the
"don't start while busy" rule; lint, tsc. **(On the PC)** lock for longer than the minimum, unlock:
card, toast, then a "Welcome back" conversation with a short summary.

### Step 6 — Skills and their rule
`skills/kairos/*/SKILL.md`, `scripts/install-skills.ps1`, the `kairos-skills` starter rule.
**Check:** a test that every SKILL.md has valid front matter (name, description ≤ 60 characters,
the four sections); policy tests for `kairos-skills`. **(On the PC)** `/kairos-code-review` on a
branch lists the planted bug and doesn't edit anything.

### Step 7 — Evaluation set
`eval/run.py`, `eval/tasks/`, `eval/fixtures/`, tests for the checks and the results file.
**Check:** the runner's own unit tests (no Hermes needed: the HTTP layer is faked). **(On the PC)**
`eval/run.py` against the real Hermes: every task's verdict recorded in the acceptance file.

### Step 8 — Acceptance (product owner, on the PC)
`docs/milestones/M5-acceptance.md`: a real return to the PC gives a correct briefing; the three
skills work on the eval fixtures; the evaluation run's results.

## 7. Definition of done

Every step check passes with recorded output, including the **(on the PC)** ones. All test suites
and linters clean. No personal data in the repo (fixtures are invented; eval results stay in
`%APPDATA%`).
