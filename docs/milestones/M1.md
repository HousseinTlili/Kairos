# M1 — Walking skeleton: Kairos talks to Hermes

Implementation spec. Read `CLAUDE.md`, then `docs/ARCHITECTURE.md` §3–6, before starting.
Work through the steps **in order, one step per session**. Every step ends with a check that
must pass before the next step begins.

Everything marked **[observed]** was recorded from a real Hermes 0.22.5 on Windows 11 and has a
sample in `fixtures/hermes-0.22.5/`. Everything marked **[documented]** comes from Hermes's docs
and has not been seen live yet; code for it must tolerate the shape being different.

---

## 1. Goal and scope

A Windows desktop app that connects to the local Hermes, sends requests, streams answers and
tool activity live, handles approvals and stop, and survives an app restart mid-run.

**In scope:** setup script, connect screen, one chat view, approval card, stop, session list,
reconnect, local `task` table.

**Out of scope for M1:** the Hermes plugin and `policy.yaml` (M2), the audit timeline (M2),
model picker (M4), voice, avatar, Linux packaging. Don't build them early.

## 5. HTTP contract [observed unless marked]

All requests except `/health` send `Authorization: Bearer <key>`. A wrong or missing key →
**401** `{"error":{"type":"gateway_auth_error","code":"gateway_auth_failed",...}}`.

| Call | Request | Response |
|---|---|---|
| Health | `GET /health` | `{"status":"ok","version":"0.22.5",...}` |
| Capabilities | `GET /v1/capabilities` | `features` object; see required list below |
| Create run | `POST /v1/runs` body `{"input": str, "session_id": str}`, header `Idempotency-Key: <task ulid>` | `{"run_id":"run_…","status":"started","replayed":false}` |
| Same key, same body | as above | `{"run_id":<same>,"status":<current>,"replayed":true}` (HTTP 202 [documented]) |
| Same key, other body | as above | `{"error":{"code":"idempotency_key_conflict",...}}` (HTTP 409 [documented]) |
| Run status | `GET /v1/runs/{id}` | `status`, `pending_controls[]`, `output`, `usage`, `execution_generation`, `admission_id` |
| Unknown run | `GET /v1/runs/{bad}` or `/events` | `{"error":{"code":"run_not_found",...}}` |
| Events | `GET /v1/runs/{id}/events` | SSE (§6) |
| Answer approval | `POST /v1/runs/{id}/approval` `{"request_id": prompt_id, "execution_generation": int, "choice": "once"\|"session"\|"always"\|"deny"}` | `{"run_id","status":"resolved","prompt_id"}` |
| Stale approval | same with wrong generation | `{"error":{"code":"stale_generation",...}}` |
| Stop | `POST /v1/runs/{id}/stop` body `{}` | `{"run_id","status":"stopping","admission_id"}` |
| Sessions | `GET /api/sessions` | `{"data":[{id, source, title, model, started_at, last_active, preview, message_count, ...}], "limit", "offset", "has_more"}` |
| Session messages | `GET /api/sessions/{id}/messages` [documented] | |

**Required capability flags** (refuse to continue, with a clear message, if any is not `true`):
`run_submission`, `run_status`, `run_events_sse`, `run_stop`, `run_approval_response`,
`approval_events`, `tool_progress_events`, `session_resources`.

**Session IDs.** Kairos generates its own: `kairos-<ulid>`. An API session cannot attach to a
session another surface owns (Desktop/CLI/TUI): Hermes answers 409 `permission_denied`
[documented]. The session list therefore shows other sessions **read-only**; only `kairos-*`
sessions can be continued.

**Run status values:** `started`, `running`, `waiting_for_approval`, `stopping`, `completed`,
`cancelled` [observed]; `failed`, `interrupted`, `unknown` [documented].

## 6. SSE parsing rules [observed]

Samples: `fixtures/hermes-0.22.5/*/0?-events.sse`.

- The stream is UTF-8 text, events separated by a blank line.
- Lines starting with `:` are comments: `: open` first, `: keepalive` every 10 s when idle
  [documented], `: stream closed` last. Ignore them (but `: stream closed` means end of stream).
- `id: N` lines precede `data:` lines; every recorded block has exactly one of each. A block
  with no `data:` line is not an event (SSE standard) and is skipped. (An earlier version of this
  spec claimed such blocks were recorded; that came from a filtered view during capture.)
- `data:` is one JSON object with an `event` field and a monotonically increasing `seq`.
- The connection closes after the terminal event (`run.completed`, `run.cancelled`, …).
- **Subscribing again replays from `seq` 0**, including past `approval.request` events (checked on
  a finished run). Buffers expire 5 minutes after the run ends [documented]; after that use
  `GET /v1/runs/{id}` instead.
- Unknown `event` values must be kept as `RunEvent::Unknown { raw }` and logged, never a parse
  error.

## 7. Event types

| `event` | Fields | Status |
|---|---|---|
| `message.delta` | `delta` | observed. After a tool call the first deltas are `"\n\n"`, which `run.completed.output` doesn't have: on completion, **replace** the streamed text with `output` |
| `tool.started` | `tool`, `preview`, `tool_call_id` | observed |
| `tool.completed` | `tool`, `duration`, `error` (bool), `tool_call_id`, `preview` | observed (`preview` was empty in all samples) |
| `approval.request` | `kind:"approval"`, `prompt_id`, `execution_generation`, `command`, `description`, `choices[]` | observed |
| `approval.settled` | `prompt_id`, `execution_generation` | observed (**no choice field**) |
| `run.completed` | `output`, `usage{input_tokens,output_tokens,total_tokens}`, `runtime`, `completed`, `partial`, `interrupted` | observed |
| `run.cancelled` | `completed:false`, `interrupted:true`, `turn_exit_reason` (`"interrupted_by_user"`) | observed |
| `run.failed`, `run.interrupted` | | documented |
| `message.interim` | `text`, `already_streamed` | documented |
| `subagent.start`, `subagent.complete` | | documented |

Every event also carries `run_id`, `timestamp` (Unix seconds, float), `seq`.

## 8. Tauri commands (Rust → TS)

```rust
connect() -> ConnectInfo                 // health + capabilities + key check
create_run(session_id: Option<String>, input: String) -> TaskRef   // {task_id, session_id, run_id}
subscribe_run(run_id: String)            // emits Tauri event "run-event" with RunEvent payloads
run_status(run_id: String) -> RunStatus
answer_approval(run_id, prompt_id, execution_generation: u32, choice: ApprovalChoice)
stop_run(run_id: String)
list_sessions() -> Vec<SessionSummary>
list_open_tasks() -> Vec<TaskRef>        // for reconnect on startup
```

Errors cross the boundary as `{ kind: "auth" | "unreachable" | "capability_missing" |
"conflict" | "not_found" | "stale" | "http" | "parse", message: string }`.

## 9. Behaviour rules (these are where bugs hide)

1. **Create the task row before calling Hermes.** `task.id` = new ULID = `Idempotency-Key`.
   On a network error, retry with the **same** key. Never invent a new key for the same request.
2. **Approval cards come from `pending_controls`, not from the stream alone.** On an
   `approval.request` event, call `run_status` and show a card only if a matching `prompt_id` is
   in `pending_controls`. Replayed streams contain old requests.
3. **Show `command` and `description` from the approval event**, not `tool.started.preview`.
   They differ: Hermes appends `; echo "EXIT_CODE=$?"` to the command it actually runs.
4. **"Denied" is not "completed successfully".** After a deny, the run still ends with status
   `completed` and a `run.completed` event. Mark the tool row as **blocked** when
   `tool.completed.error == true` follows a denied approval for that run, and show the task as
   "Completed — 1 action blocked", not a plain success.
5. **Stop:** send `stop_run`, show "Stopping…", wait for `run.cancelled` or status `cancelled`.
   The in-flight tool reports `error: true`; display it as "stopped", not "failed".
6. **Reconnect on startup:** for each task with a non-terminal status, call `run_status`.
   Terminal → store the outcome. Non-terminal → `subscribe_run`. `run_not_found` → mark the task
   `lost` and show it; never resubmit automatically.
7. **`unknown` status** [documented]: show "Hermes restarted during this request; outcome
   unknown" with an Acknowledge button (`POST /v1/runs/{id}/resolve-unknown`, M1 may stub this
   with a message). Never resend.
8. **The key never reaches the web view, logs, or error messages.** Redact `Authorization`
   headers in any debug output.
9. **Ignore `runtime.provider` / `runtime.model`**: they are empty strings on this install.
   Show the model from the session list instead.
10. **`/v1/skills` returns HTTP 500 on Hermes 0.22.5** (a Hermes bug:
    `find_all_skills() got an unexpected keyword argument 'include_editorial'`). M1 does not use
    it. Later features must treat it as optional.

## 11. Steps

Each step: implement, run its check, commit with a clear message. Don't start the next step
with a failing check.

### Step 1 — Scaffold
Create `app/` with `pnpm create tauri-app` (React + TS template), add the crates and packages
from §3, the folder layout from §4, ESLint/Prettier, and `cargo clippy` clean.
**Check:** `pnpm -C app tauri dev` opens an empty Kairos window; `cargo test` and
`pnpm -C app test` run (zero tests is fine).

### Step 2 — `scripts/setup.ps1`
Idempotent PowerShell script:
1. Resolve `HERMES_HOME`; fail clearly if `config.yaml` is missing.
2. If `.env` lacks `API_SERVER_ENABLED=true`, `API_SERVER_HOST=127.0.0.1` or an
   `API_SERVER_KEY` ≥ 32 hex chars: back up `.env` to `.env.bak-kairos-<yyyyMMddHHmmss>`, add or
   replace those lines (generate the key with `RandomNumberGenerator`, 32 bytes, hex), run
   `hermes gateway restart`.
3. Poll `GET /health` up to 30 s.
4. Print version and approval mode (`hermes config get approvals.mode`). Never print the key.
**Check:** run it twice; the second run changes nothing and doesn't restart Hermes.

### Step 3 — Hermes client and SSE parser (Rust)
`HermesClient` with the calls in §5, the parser in §6, `RunEvent` in §7.
**Check:** `cargo test` with tests that parse **every** `.sse` file in `fixtures/` and assert the
exact event sequence per file (e.g. `run-approval-deny`: `tool.started`, `approval.request`,
`approval.settled`, `tool.completed{error:true}`, `run.completed`). Unit tests for the
empty-`id:` block, comments, unknown event, and a stream cut mid-event.

### Step 4 — Key handling and Connect screen
On first launch, read `API_SERVER_KEY` from `%HERMES_HOME%\.env`, store it in the keyring, use
the keyring afterwards. Connect screen shows: Hermes reachable yes/no, version, missing
capabilities, and a warning banner if approval mode is not `manual` (D-009: `smart` can
auto-approve destructive commands until M2; `off` and YOLO are never acceptable). Read the mode
with `hermes config get approvals.mode`; the API doesn't expose it (`admin_config_rw: false`).
**Check:** with Hermes running → green with version `0.22.5`. Stop Hermes (`hermes gateway stop`)
→ "Hermes isn't running" with the command to start it. Put a wrong key in the keyring →
"Key rejected", with a button that re-reads it from `.env`.

### Step 5 — Chat with streaming
New conversation → `create_run` → stream deltas into the message; tool rows for
`tool.started`/`tool.completed`. Task row written and updated.
**Check:** "Reply with exactly: Kairos OK" streams and completes. "List the files in
C:\Windows\Temp" shows a `terminal` tool row then the answer.

### Step 6 — Approval card
Implement rules 2–4 of §9. Buttons: Allow once, Allow for this session, Always allow, Deny.
**Check:** with approval mode `manual` (confirm with `hermes config get approvals.mode`), ask
Kairos to delete a scratch folder you created → card shows the real command → Deny → folder still
exists, task shows "1 action blocked". Repeat with Allow once → folder gone.

### Step 7 — Stop and reconnect
Stop button (rule 5) and startup reconnect (rules 6–7).
**Check:** ask for `ping -n 40 127.0.0.1`, press Stop → "Stopped" within a few seconds. Start the
same request, close the app after 5 s, reopen → the run is found and its result shown.

### Step 8 — Session list
Sidebar from `list_sessions`, newest first. `kairos-*` sessions open and continue; others are
shown greyed out, read-only, labelled with their source.
**Check:** your Desktop conversations appear read-only; a Kairos conversation continues with
context ("what did I just ask you?").

### Step 9 — Live integration test and acceptance
A Rust integration test marked `#[ignore]` that runs against the real local Hermes:
health, capabilities, a simple run end to end, idempotent retry. Run with
`cargo test -- --ignored`. Then walk the ROADMAP M1 acceptance list by hand and record the
result in `docs/milestones/M1-acceptance.md` (date, Hermes version, pass/fail per item).

## 12. Definition of done

- All step checks pass; `cargo clippy -- -D warnings`, `cargo test`, `pnpm -C app test` and lint
  are clean.
- `M1-acceptance.md` exists with real results, including any failures.
- No secrets, user names or session data committed (`fixtures/README.md` check passes on the
  whole repo).
