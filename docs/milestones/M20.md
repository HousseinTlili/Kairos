## 1. Goal and scope

Kairos can open and close apps and capture the screen. The goal is for it to **use** an app: read
what's in a window, click, type, beside you, without taking your cursor or keyboard. You see which app
it's in, you can stop it at any moment, and it asks before anything it does.

Example: "In Notepad, change every date in this file to next week's."

**In scope:** rules for Hermes's `computer_use` tool, cards that say what will happen, a working-in
line and Stop on the top bar, a badge for waiting approvals, a switch that's off by default.

**Out of scope:**
- Working without you: no computer use in scheduled jobs, or from Telegram or the Hermes command line.
- A virtual desktop for Kairos, or a second screen for it to work on (Hermes's Bot Desktop is Linux).
- Admin windows: the driver can't reach them. Password entry: it has none, by design.
- Any change to Hermes or to `cua-driver`. Nothing to install: `cua-driver` 0.21.0 is already here.

## 2. What Hermes offers (read from its source 2026-11-01, Hermes 0.22.5)

One tool, `computer_use`, with an `action`:

| Action | Hermes's own gate | What it does |
|---|---|---|
| `capture` | **None, "free"** | Screenshot and/or accessibility tree of a window; `app='screen'` is the whole screen, `app='desktop'` the taskbar and icons |
| `list_apps`, `list_windows`, `wait` | None | What it says |
| `focus_app` | Only with `raise_window` | Sets which app input goes to |
| `click`, `double_click`, `right_click`, `middle_click`, `drag`, `scroll`, `type`, `key`, `set_value` | Asks | Input, by default to the window in the background |

- **Its grants are per kind of action:** the key is `cua:<action>:<background|foreground>`. One "always"
  on `type` would cover all typing, in every app, for good. Foreground has its own key.
- **Hard blocks, before any prompt:** a few logout and lock key combinations, and a few shell patterns
  in typed text (`curl … | bash`). Short lists, written mostly for macOS and Linux.
- **Nobody to ask means refused.** The gate is the same one as for terminal commands.
- **`--yolo` swaps the driver to an unrestricted mode.** CLAUDE.md already forbids it.
- **Turning it on:** `hermes tools enable computer_use --platform api_server`. Today it's on for the
  command line and off for the API Kairos uses.
- **Where the target is:** `capture` or `focus_app` sets a "sticky" app in Hermes's backend, and input
  goes there. The tool call itself often names no app: `click(element=12)`.

**What this means for Kairos's design, none of it in the plan of 2026-11-01:**

1. **It can reach everything the other rules guard.** Clicking and typing go round every rule that reads
   a tool's arguments. So, unless stopped, the model could:
   - click **Allow on Kairos's own approval card**, or switch off a rule in Settings ▸ Rules;
   - type `hermes config set approvals.mode off` into a terminal, past `no-safety-changes`;
   - press Win+R and run anything;
   - buy something in a browser, past the M12 rules.

   So some windows must be off limits entirely (§4). Asking isn't enough for these: a card that reads
   "Click element 12" gives you no way to see this happening.
2. **The rules must know the target, and the call doesn't say it.** The plugin has to work it out, and
   refuse when it can't (§4).
3. **Kairos's own `ask` would mean two cards for every click.** A Kairos rule that asks and Hermes's gate
   are independent, as `run-kairos-rule-double-prompt` records. So Kairos rules only **refuse** input;
   Hermes's gate asks, once. `capture` has no gate, so there a Kairos rule asks.
4. **Hermes's card says little.** Its text is built in the tool, and the plugin can't change it. The
   words have to come from what Kairos can see (§3, and a probe).
5. **What's captured goes to your AI provider.** A screenshot of a window is sent to the model like any
   other tool result. With a cloud model, that's the provider's servers.

**What the probes added (Step 2, 2026-11-01, in Character Map):**
- **Approvals reach Kairos as ordinary `approval.request`s,** one card per action, with choices `once`,
  `deny`, `session`, `always`. `smart` didn't approve any by itself: Hermes's gate for this tool has no
  helper step (`_run_approval_gate`). Input really does stay in the background: no focus was taken.
- **Stop works on a waiting card:** `run.cancelled`.
- **The stream says nothing about the target.** `tool.started` has an empty preview, except `type`'s text.
  Hermes's card says `computer_use: click element #1`, and cuts typed text at 60 characters. The element's
  name and the app are only in what the plugin sees, so the plugin puts them in the audit row (`args_redacted`:
  `kairos_target`, `kairos_element`) and the card reads them there.
- **A capture's result** has `app` (as asked), `elements` with `index`, `role`, `label`, and an empty
  `window_title`; a failed one has width 0 and a message. Indices change between captures.
- **`list_windows` gives every open window's title,** and `list_apps` every app's path, with your user
  name. **This spec had them free, which was wrong:** they now ask. The first probe sent the
  titles to the model before this was seen.
- **Changing that list costs `config.yaml` comments:** `hermes tools enable`, `config unset`, and `config set` on a
  list already there each removed the same 236 lines of commented-out template, which Hermes's writer ties to it
  (seen; the backup was put back). No setting changes, and the text stays in `cli-config.yaml.example`. Also, after
  first use, an explicit list of toolsets stays in the file, so a toolset a later Hermes adds won't appear by itself.
- **Turning it off needs no restart:** a new run no longer had the tool, gateway untouched.
- **A minimised window can't be seen** ("no on-screen window"), though the schema says otherwise.
- **Names:** `app` takes the process name (`charmap.exe`); the window's title ("Character Map") wasn't found.
- **The `tool_call` route is covered:** Hermes unwraps it before the hooks, so rules see `computer_use`.
- **Each step costs a full turn:** about 22,000 input tokens each on the default model, 200,000 for a five-step
  task. The switch's page says so.
- **Notepad wasn't used:** it would have reopened 22 saved tabs. Character Map has nothing personal in it.

## 3. What you see

**Settings ▸ Safety ▸ Computer use.** One switch, off by default, with what it means in a sentence;
whether `cua-driver` is ready; "Restart Hermes" when the change needs it; and the list of apps it may
never touch, which is the rule below and edits like any other rule.

**In a conversation.** Two kinds of card:
- **Seeing a window:** "Let Kairos see **Notepad**? The picture goes to your AI provider." Choices:
  Once, or For this conversation. One grant covers that one app.
- **Acting:** "**Click Save** in **Notepad**", as far as the probes allow. Choices: for clicks and
  scrolling Once or For this conversation; for **typing and keys, Once only, and the card shows the
  exact text**. "Always" is never offered for `computer_use`.

**On the top bar.** While it's at work: "Working in Notepad" and **Stop**. Stop ends the request with
the same call as the chat's Stop. A **badge** on the bar and in the sidebar counts approvals waiting;
a click brings up the conversation. It matters here: while Kairos works in another app, you may not be
looking at Kairos.

**In the timeline.** Each action is a tool row in those same words. Every decision goes in the audit log,
as usual.

## 4. How it works

**The plugin works out the target** (`plugin/kairos/desktop.py`, standard library only, pure parts tested):
- `capture` with `app`: that app. Without it: the foreground window's process and title, through
  `winapps`.
- It remembers each conversation's last target. Input with no `app` uses that, and input naming an app
  checks that one too.
- **No known target: refused,** with "capture the window first". A stale or wrong guess is the danger, so
  the plugin also checks the result of each `capture` where the probe shows the real app is there.
- **Known limit:** the plugin sees the call, not the driver. A dialog that opens after a click, or a
  window that changes title, can differ from what it remembers. The cards and the deny rule on a fresh
  capture are the defence; it isn't airtight, and the page says so in one line.

**New match kinds in the rules:** `actions` (the `action` argument, exactly) and `targets` (globs over the
worked-out process name and window title). `any_text` won't do: a click with `app: "capture"` would match
a rule meant for captures. Added to `policy.py`, the Rules page's model, and their tests.

**Two refusals aren't rules, because they can't sensibly be edited:** input with no known target, and typed
text that looks like a key or token (`redact.py`'s patterns).

**New starter rules, in this order** (delivered through "Add the new rules"):

| Rule | Applies to | Action |
|---|---|---|
| `computer-use-off-limits` | Targets: Kairos itself, Hermes Desktop, Claude; terminals and shells, code editors with a terminal; File Explorer (its address bar runs programs); Settings, Registry Editor, Task Manager, Group Policy; Windows Security; password managers; **browsers** (§7 question 4); titles naming banks and payment sites | **Deny** |
| `computer-use-whole-screen` | `capture` of `screen` or `desktop`, and input to `desktop`: the screen holds whatever else you have open, and `screen_capture` already exists and asks | **Deny** |
| `computer-use-keys` | `key` with Win held, Ctrl+Shift+Esc, Ctrl+Alt+Del: they open what the first rule shuts | **Deny** |
| `computer-use-list` | `list_apps`, `list_windows`: every window's title and app's path go to the provider | **Ask**, once per conversation |
| `computer-use-see` | `capture` | **Ask**, once per app and conversation: its approval key is rule + app, rather than the exact call |

All other input falls through to Hermes's gate, which asks. `computer_use` joins `KAIROS_TOOLS`, so only Kairos's conversations can use it
(D-032), which also closes the command line, where it runs today with no rule behind it.

**The cards.** `turn.ts` reads the approval and builds the words from the conversation's last target and,
if the stream carries it, the name of the element. If the words can't be found, the card shows the
target and Hermes's own text, never a guess. The approval's offered choices are filtered in the card.

**Stepping aside.** The bar and quick box hide only for a capture that could include them. With
`computer-use-whole-screen` in place, that's nothing new; `hidesForCapture` stays as it is unless the
probe shows otherwise.

**The switch.** A small `computer_use.rs`, `skills.rs`'s way: `hermes config set platform_toolsets.api_server` with
the current list (`hermes tools list --platform api_server`), with or without `computer_use`. It won't turn on
without the off-limits rule. Readiness comes from `hermes computer-use status`.

**Scheduled and automation requests.** Jobs aren't Kairos conversations, so they're refused. An automation's
"Ask Kairos" is, and it waits for your card like anything else (D-033: an automation never approves).

## 5. Decisions

- **D-040 — Kairos's computer use: off by default, some windows off limits, Hermes's gate asks — Accepted.**
  Hermes's `computer_use` can be turned on for Kairos's own conversations from a switch. D-014's "stays off
  until there is a use case and a rule set" is met by this, not overturned. Clicking and typing go round
  every rule that reads a tool's arguments, so the plugin works out the target window and refuses Kairos
  itself, terminals, security tools, password managers, browsers and banking; input it can't place is
  refused. Hermes's gate asks for every action, once, so no double cards; typing is never granted beyond
  once, and "always" is never offered.

## 7. Ask the product owner, don't guess

1. **Kairos may switch `computer_use` on and off for `api_server`, from your click, and for the probe.** It's
   a change to Hermes's configuration, and the probe drives a scratch Notepad on your desktop, in the
   background, while you watch. Recommended: yes.
2. **Seeing a window.** Hermes treats it as free, but the picture goes to your AI provider.
   Recommended: **ask once per app per conversation.** Stricter: every capture, which is a card before nearly
   every action. Looser: free, which would let the model look at any window unasked.
3. **Hermes's command line loses `computer_use`.** It's on there today with no rule behind it; Kairos's
   rules refuse it unless the conversation is Kairos's. Recommended: yes. If you use it there yourself, say so
   and it stays, with the off-limits rules.
4. **Browsers off limits.** Clicking in a browser goes round the M12 rules, including the ones about paying, so
   Kairos would use its browser tools for the web instead. The cost: it can't work in your own open browser
   window. Recommended: off limits. The list is a rule, so you can edit it later.
5. **Which apps count as off limits.** §4's list is a starting point, and any banking app you use by name
   should go on it: a title match only catches what says "bank". Recommended: start with §4, and add yours.
