# M17 — Automations on events

Implementation spec. Read `CLAUDE.md`, `docs/milestones/M3.md` §7–8 (alerts, presence events) and
`docs/milestones/M5.md` §2 (the briefing, the first thing Kairos does by itself) first.

**Status (2026-10-30):** spec only, on `m17/automations` (stacked after `m16/themes`), at the
product owner's request: the Herald OS idea of *automations that run when you log in, come back
after a break, the battery runs low or a program crashes*. D-033 is Proposed; §7 lists what to
decide before building.

---

## 1. Goal and scope

Settings ▸ Kairos ▸ **Automations**: rules of the form **when** something happens on the PC,
**only if** some conditions hold, **do** one or more things. Examples:

- *When I log in on a weekday morning, open Outlook and Teams.*
- *When a program crashes, offer to have Kairos explain why* (Herald OS's crash flow).
- *When the battery drops under 15 %, say so in Kairos's voice.*
- *When I join my home Wi-Fi after 18:00, ask Kairos what's left on today's calendar.*
- *When I unplug the charger, show the time left on the island.*

**Out of scope:**
- **Times of day without an event** ("every day at 08:00"). Hermes's scheduled jobs do that
  already (M8 §5), and they stay the place for it.
- **Writing automations by talking to Kairos** ("Kairos, whenever I…"). It would need a plugin tool
  that hands a draft to the app for approval; it's a later step once the editor exists.
- **Running scripts or shell commands as an action.** Hermes's tools under the Kairos rules do that,
  through "Ask Kairos".
- **"Pick up where you left off"** (the other Herald idea). It's a separate feature.

The welcome-back briefing (M5) stays as it is, with its own settings. It's the model for this
milestone, not part of it.

## 2. What Kairos already notices (read 2026-10-30)

| Event | Where it comes from today |
|---|---|
| Login (Kairos started at login) | `presence.rs`: `startup` with detail `autostart` |
| Back after a break (resume from sleep, unlock) with the time away | `presence.rs`: `resume`, `unlock`, `away_s` |
| Battery low / critical, disk nearly full, a process hogging the CPU | `system/alerts.rs` (with hysteresis, one alert per episode) |
| Charger plugged / unplugged, Wi-Fi network | the system snapshot (M3), read every 15 s; nothing compares two snapshots yet |
| A program crashed or hung | **not yet.** Windows writes it to the Application event log: provider *Application Error*, event 1000 (crash), and *Application Hang*, 1002. Readable without admin rights (checked on the PC 2026-10-30: RuntimeBroker, nvcontainer and nasm crashes in October) |

## 3. Automations

### 3.1 When (one trigger each)

| Trigger | Settings | Fires |
|---|---|---|
| **Login** | — | once, when Kairos starts at login |
| **Back at the PC** | away at least *N* min (default 30) | on resume or unlock after that long |
| **Battery low** | under *N* % (default 15) | once per discharge, when it crosses the level |
| **Charger** | plugged in / unplugged | on the change |
| **Wi-Fi** | joined *network* / disconnected | on the change; the network list comes from the snapshot |
| **Disk nearly full** | — | with the existing alert |
| **A program crashed or hung** | any / these programs; ignore list | per event; a burst from one program counts once (60 s) |

The crash trigger ignores, by default, Windows's own background processes (a starter list:
`RuntimeBroker.exe`, `svchost.exe`, `backgroundTaskHost.exe`, `SearchHost.exe`, …) and Kairos
itself. The Master can add names. It carries the program's name, version, the faulting module and
the exception code, from the event; never a memory dump.

### 3.2 Only if (all optional)

- between two times of day; on chosen days of the week;
- on battery / plugged in;
- **not during quiet hours** (the briefing's, M5), on by default for every automation. An automation
  can be allowed through quiet hours one by one.

### 3.3 Do (one or more, in order)

| Action | What it does | AI |
|---|---|---|
| **Notify** | a Windows toast with the Master's text | no |
| **Say** | Kairos says the Master's text in its voice (M9 TTS) | no |
| **Show on the island** | the pill shows the text for 10 s | no |
| **Open an app** | starts an app picked from the Start menu (the M15 pinned-apps catalog) | no |
| **Offer to ask Kairos** | a toast with an **Ask Kairos** button; the request starts only on the click | on click |
| **Ask Kairos** | starts a request with the Master's own text, in a conversation named after the automation | yes |

Texts can hold placeholders filled from the event: `{battery}`, `{time_left}`, `{away}`, `{network}`,
`{program}`, `{crash}` (the crash event as data). For "Ask Kairos" they go in as quoted data, as
the briefing's facts do (M5 §2.3), so the event text can't speak as the Master.

### 3.4 What keeps them safe

- **The rules apply as in any request.** "Ask Kairos" runs in a `kairos-` conversation (so Kairos's
  PC tools work, D-032), with the Master's rules in front of Hermes; anything a rule makes ask
  shows an approval card and a toast, and **waits for the Master**. An automation never approves
  anything, and Kairos never switches the approval mode.
- **No resent work.** Each request is created with an `Idempotency-Key` stored first (M1 §9 rule 1).
  A request that fails is recorded as failed, not retried.
- **One at a time.** If a chat request or another automation's request is running, an "Ask Kairos"
  waits up to 5 min, then is skipped and recorded as skipped.
- **Limits.** Each automation has a cooldown (default 10 min, at least 1). Across all automations, at
  most **6** AI requests an hour and **30** a day; past that they're skipped and recorded.
- **No loops.** An automation's own actions never trigger automations (the apps it opens aren't
  watched, and Kairos's own crashes are ignored).
- **History.** Every firing is recorded in `kairos.db`: time, automation, the event (as shown in the
  editor, no notification text), and the outcome: done, skipped (with the reason), or failed.
  Settings shows the last 100.
- **Off switch.** One switch at the top turns every automation off at once.

## 4. Where it runs

- **The decision is in the Rust core** (`automations/`): the triggers come from threads that are
  there already (presence, system snapshot, alerts) plus a new event-log watcher for crashes. One
  pure function, `automations::rules::decide(automation, event, now, history)`, checks the
  conditions, quiet hours, cooldown and limits, and is tested without Windows.
- **Actions without AI run in the core** (toast, voice, island, opening an app). **"Ask Kairos"** is
  sent to the main window as an `automation-ask` event, and the window starts it through the chat
  code, like the briefing's summary, so the request, its approval cards and its cost line are the
  usual ones.
- **Storage:** `kairos.db`, tables `automations` (one row each, its definition as JSON, versioned)
  and `automation_runs` (the history).

## 5. Decisions

- **D-033 — Automations are Kairos's own: events from the PC, decided in the core, with AI requests
  under the usual rules — Proposed.** Hermes's scheduled jobs only know the time; the events are
  local Windows facts Hermes doesn't see. So Kairos keeps the automations, decides them with one
  tested function, and sends only "Ask Kairos" to Hermes, as a normal request: the rules, approvals,
  idempotency and the D-032 scope all hold. Crashes are read from the Application event log with
  the `Win32_System_EventLog` feature of the `windows-sys` crate already used (a new feature, not
  a new crate). Taken from Herald OS (2026-10-30), whose README lists automations for login,
  return, low battery and crashes, and offers to explain a crash.

## 6. Steps

### Step 1 — Spec, D-033
This document. **Check:** the product owner accepts it or changes it (§7).

### Step 2 — Model, storage and the decision
Types for triggers, conditions and actions (Rust and `features/automations/model.ts`, kept in
step), the two tables, `decide` with quiet hours, cooldown and the hourly and daily limits.
**Check:** unit tests: "an automation in its cooldown is skipped with the reason", "the seventh AI
request in an hour is skipped", "quiet hours hold back a toast but not an automation allowed through".

### Step 3 — Triggers from what Kairos already notices
Login and back-at-the-PC from presence; battery and disk from the alerts; charger and Wi-Fi by
comparing two snapshots. **Check:** tests on recorded snapshot pairs ("unplugging fires once, not
every 15 s"); a live log of the events while plugging and unplugging **(on the PC)**.

### Step 4 — Crashes
An event-log watcher (subscription to the Application log, *Application Error* 1000 and *Application
Hang* 1002), the ignore list, and 60 s de-duplication. **Check:** parsing tests on sanitised event XML
in `fixtures/`; a test program that crashes on purpose fires "A program crashed" once **(on the PC)**.

### Step 5 — Actions and history
Toast, voice, island, opening an app, the offer, and "Ask Kairos" with its waiting, limits and
idempotency; every outcome in `automation_runs`. **Check:** tests ("an Ask Kairos while a chat runs
waits, then is skipped"); a live "Ask Kairos" that hits an asking rule shows the card and waits
**(on the PC)**.

### Step 6 — Settings ▸ Automations
The list (switch, last run), the editor (When / Only if / Do, with a **Test now** button that fires
it with a sample event marked as a test), the history, and the off switch. **Check:** tests and
screenshots of each part in dark and light.

### Step 7 — Starters
Three, offered in the list: **A program crashed → offer to ask Kairos** (on, if §7 agrees),
**Battery under 15 % → say it** (off), **Login → open apps** (off, no apps chosen yet).
**Check:** a fresh profile shows the three.

### Step 8 — Acceptance (product owner, on the PC)
The checks above, added to `docs/TESTING.md`, with `M17-acceptance.md`.

## 7. Ask the product owner, don't guess

1. **"Ask Kairos" without a click.** Recommended: allowed, since the Master wrote the automation and
   the rules still ask for anything risky. The stricter choice is "offer only": every AI request
   needs a click.
2. **The crash starter on by default?** Recommended: yes, as an offer (a toast with a button, no AI
   until the click).
3. **The limits:** 6 AI requests an hour, 30 a day, 10 min cooldown by default. Recommended as is.
4. **The `Win32_System_EventLog` feature** of `windows-sys` for crashes (no new crate). Recommended:
   yes; without it there is no crash trigger.

## 8. Definition of done

Every step's check run and shown; the (on the PC) checks in `docs/TESTING.md`; D-033 Accepted;
tests, lint and clippy clean; committed on `m17/automations`, not pushed.
