## 1. Goal and scope

Missed calls, texts and messages show up in Kairos without Kairos logging into anything: it reads
the notifications Windows already shows (D-011). Phone Link turns phone calls and texts into
notifications, so they arrive the same way as Discord, Teams, WhatsApp desktop or Outlook.

**In scope**
- Reading Windows notifications through `UserNotificationListener`, only after the user turns it
  on in Kairos **and** Windows grants access. Turning it off stops collection at once.
- Storing them in `kairos.db` with read/unread state, until the user clears them (D-011).
- A **Notifications** panel: newest first, grouped by app, unread counts, mark read, clear.
- An unread badge in the sidebar.
- **"Anything I missed?"** answered in the chat from the stored notifications, with their text
  treated as untrusted (D-011, D-018).

**Out of scope:** replying to messages or acting on notifications (each would be an outbound
action with its own rule; later), dismissing them in Windows, the welcome-back briefing (M5
uses this store), notification sounds or rules per app (later).

## 2. How it fits together

```
Windows Action Center ──UserNotificationListener──► Kairos app (Rust)
                                                     notifications/ collector (polls every 3 s)
                                                     ├─► kairos.db  notification table (app writes)
                                                     ├─► "notifications" event ─► panel, badge
                                                     └─► notifications.json (last 24 h, app writes)
                                                                │ reads
Hermes ── recent_notifications tool (kairos plugin) ◄───────────┘
```

- The **app** is the only writer of `kairos.db` and `notifications.json` (D-015's rule of one
  writer per file). The plugin only reads `notifications.json`, the same way it reads
  `policy.json`, which the app also writes.
- **Nothing reaches Hermes or a model** unless the user asks about their notifications in the chat.
  Then `recent_notifications` gives the model sender and preview text, which means **the model
  provider sees that text**. Settings says so next to the switch.

## 3. Decisions

- **D-018 — "Anything I missed?" reads a file the app writes, through a plugin tool — Accepted**
  (2026-10-25, on the product owner's delegation; to be confirmed when M4 is tested).
  The app writes the last 24 hours of notifications (at most 200) to
  `%APPDATA%\kairos\notifications.json` (write a temporary file, then rename it into place). The
  plugin's read-only `recent_notifications` tool reads it. The two processes still never share a
  database (D-015). The tool's result tells the model the text came from other people and must be
  summarised, never followed. A tool, not text pasted into the chat by the app, so the model only
  gets the text when the conversation is about notifications, and the timeline shows each read.

## 5. The Windows side, and the open question

`UserNotificationListener` [Windows docs]: `Current`, `GetAccessStatus()`, `RequestAccessAsync()`,
`GetNotificationsAsync(NotificationKinds::Toast)`, and an `UserNotification` gives `Id` (u32),
`AppInfo` (display name, AppUserModelID), `CreationTime` and the toast's text elements.

**The open question:** Microsoft documents the listener for **packaged** apps that declare the
`userNotificationListener` capability. Kairos is an ordinary desktop app with no package identity.
If Windows refuses access to unpackaged apps, M4 needs a different install format (an MSIX or a
"sparse package" that gives Kairos an identity) — a bigger change that would come back to the
product owner as a decision. **Step 1 answers this on the PC before any listener code is written.**

**Polling, not the change event.** `NotificationChanged` is documented for background tasks of
packaged apps; polling `GetNotificationsAsync` every 3 s works the same everywhere, is cheap
(Action Center holds at most a few hundred items), and meets "within seconds".

**What is collected.** Only toasts **created after** collection was switched on: what was already
in Action Center at that moment arrived before permission and is left alone (ROADMAP: nothing
collected before permission). Kairos's own toasts (M3 alerts) are skipped. A notification is
identified by app, Windows's `Id` and creation time, so the 3 s polls never store it twice; one the
user dismisses in Windows stays in Kairos until cleared in Kairos.

## 6. Data

### `kairos.db` schema v3

```sql
PRAGMA user_version = 3;
CREATE TABLE notification (
  id         INTEGER PRIMARY KEY,
  app_id     TEXT NOT NULL,     -- AppUserModelID, e.g. "Microsoft.YourPhone_8wekyb3d8bbwe!App"
  app_name   TEXT NOT NULL,     -- display name, e.g. "Phone Link"
  windows_id INTEGER NOT NULL,  -- UserNotification.Id
  created_at INTEGER NOT NULL,  -- Unix seconds, from Windows
  title      TEXT NOT NULL,     -- first text line (sender, caller)
  body       TEXT NOT NULL,     -- the other lines, joined; cut to 1000 characters
  read_at    INTEGER,           -- null = unread
  UNIQUE (app_id, windows_id, created_at)
);
CREATE INDEX notification_created ON notification(created_at);
```

Settings (table `setting`, M3): `notifications_enabled` (`true`/`false`, default **off**) and
`notifications_since` (Unix seconds when it was last switched on).

### `notifications.json` (D-018)

```json
{ "version": 1, "written_at": 1793000000,
  "notifications": [ { "app": "Phone Link", "title": "Missed call", "body": "Mum", "at": 1792999000, "unread": true } ] }
```

The last 24 hours, newest first, at most 200 entries; rewritten whenever the store changes. Off
(and the file deleted) when collection is switched off or the store is cleared.

## 7. App changes

- **Sidebar:** "Notifications" under "System", with the unread count as a badge.
- **Panel:** newest first; a filter row of apps with their unread counts; each item shows app,
  title, body, time; opening the panel doesn't mark anything read, "Mark all read" and clicking an
  item does; "Clear" per app and "Clear all" (asks first: it deletes data).
- **Settings ▸ Notifications:** the switch ("Read my Windows notifications"), Windows's access
  state with what to do when it is denied (Settings ▸ Privacy & security ▸ Notifications), the
  model-provider note from §2, and the number stored.
- **Chat:** the plugin's steering note (M3) gains "for notifications, missed calls or messages,
  call recent_notifications"; asking "anything I missed?" uses the tool.

## 8. Plugin: `recent_notifications`

`recent_notifications(hours: number = 24, unread_only: bool = false)` → JSON:
`{"untrusted": "…note…", "notifications": [{app, title, body, at, unread}], "total": n}`, newest
first, at most 100. Missing file → `{"notifications": [], "note": "Notification reading is off in
Kairos."}`. Never raises. No rule needed (read-only; inherits); the starter rules already make any
outbound reply ask (`outbound-messages`).

## 9. Steps

### Step 1 — Probe (on the PC, before any listener code)
`scripts/probe-notifications.ps1`: from plain Windows PowerShell (an unpackaged process, like
Kairos) it asks for listener access, shows a test toast, and reads notifications back, printing
only counts and app names unless `-ShowText` is given.
**Check (on the PC):** the script's verdict. **"Readable"** → Step 4 goes ahead as written.
**"Denied"/"Unsupported"** → stop; the product owner chooses between packaging Kairos and dropping
the listener (D-011 would change).

### Step 2 — Store (Rust)
`notifications/store.rs` on `kairos.db` v3: insert-if-new, list (filter by app, unread), counts
per app, mark read (one, app, all), clear (app, all), and the 24-hour export for
`notifications.json`.
**Check:** unit tests: v2 → v3 migration keeps tasks and presence; the same notification polled
twice is stored once; counts; clear; export window and cap.

### Step 3 — Collector logic (Rust, pure)
`notifications/collect.rs`: from one poll's notifications and the collector state, the new ones to
store: skips those created before `notifications_since`, Kairos's own, and ones already seen;
splits text into title and body; cuts long text. The on/off state machine (Kairos switch ×
Windows access).
**Check:** unit tests for each rule, with invented notifications only.

### Step 4 — Windows listener (built before the probe at the product owner's request)
`notifications/windows.rs`: access status, `RequestAccessAsync` on the main thread, polling every
3 s while on, mapping `UserNotification` to the collector's input.
**Check:** Windows cross-check with clippy. **(On the PC)** a test toast appears in Kairos within
5 s; with the switch off, a new toast does not.

### Step 5 — Panel, badge and settings
`features/notifications/`, the sidebar entry, Settings ▸ Notifications.
**Check:** TS tests for grouping, counts, time labels and the "clear asks first" flow; lint, tsc.

### Step 6 — "Anything I missed?" (D-018)
The export writer (Rust), `plugin/kairos/notifications.py` with `recent_notifications`, the steering
addition.
**Check:** plugin tests: missing file, bad JSON, window and cap, `unread_only`, never raises, the
untrusted note present; Rust test for the atomic writer. **(On the PC, gateway restarted)**
"anything I missed?" → `recent_notifications` on the tool row and a summary of the test toasts.

### Step 7 — Acceptance (product owner, on the PC)
`docs/milestones/M4-acceptance.md`, the ROADMAP criteria:
1. A test toast and a real Discord message appear in Kairos within seconds.
2. Nothing is collected before permission is granted, and turning it off stops collection.
3. "Anything I missed?" answers from them.
