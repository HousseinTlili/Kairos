# Kairos Decisions

Each decision records what was chosen, what else was considered, and why. Status is **Accepted**
(the product owner agreed), **Proposed** (awaiting approval), or **Open** (needs an answer).

---

## D-001 — Hermes Agent is the engine, used unmodified — Accepted

**Decision.** Kairos runs Hermes Agent as a separate process and extends it only through its
documented API server and plugin system. No fork, no copied core code.

**Alternatives.**
- *Write our own agent core* (the original ChatGPT Phase 0 plan): months of work to rebuild
  what Hermes already has, before Kairos does anything useful.
- *Copy selected Hermes modules into Kairos*: Hermes is ~21k files and ~10k Python files, and its
  modules depend on shared profile, secret-scope and path plumbing. Example: the approval system
  (`tools/approval.py`) is a front file plus about 8 helper files that pull in the config, i18n
  and gateway modules. Extracting one piece drags much of the codebase along.
- *Fork Hermes*: every Hermes release becomes a merge. Hermes changes quickly.

**What Hermes already covers that Phase 0 planned to build:**

| Planned capability | In Hermes |
|---|---|
| Model abstraction and routing | ~40 provider plugins, fallback providers, per-request model choice |
| Tool layer and dangerous-action approval | Tool registry; approval gate with `smart`/`manual`/`off`, hardline blocklist, deny rules, allowlist |
| Crash-safe execution | Idempotency ledger, `unknown` run state, checkpoints and rollback |
| Memory | Built-in memory plus pluggable providers |
| Background and scheduled work | Cron jobs, Jobs API, kanban board, subagent delegation |
| Skills | 58 installed locally (MIT, markdown) |

**Consequences.** Kairos is coupled to Hermes's API and hook contracts (listed in
`ARCHITECTURE.md` §3). We pin a tested version range and test upgrades before taking them.

## D-002 — Standalone desktop app, not a Hermes Desktop plugin — Proposed

**Decision.** Kairos ships its own desktop app built with **Tauri 2 + React + TypeScript**.

**Alternatives.**
- *Hermes Desktop plugin* (`@hermes/plugin-sdk`, a single ESM file in `desktop-plugins/`): far
  less work and hot-reloads, but Kairos would be a pane inside Hermes's app, not its own product.
  Worth keeping in mind as a quick prototyping surface.
- *Web UI in the browser first*: simplest to build, but no OS keyring, tray or notifications.
- *Electron*: heavier; Tauri was already the stated preference.

**Why Tauri works well now.** The earlier objection to Tauri was bundling a Python backend
inside it. With Hermes as the engine there is **no Kairos Python server**, so Tauri only wraps a
React UI plus a small Rust layer (HTTP client, keyring, read-only SQLite).

## D-003 — Talk to Hermes over the Runs API — Proposed

**Decision.** Use `/v1/runs` (+ SSE events, approval, clarify, stop, resolve-unknown) and
`/api/sessions` as the primary interface.

**Alternatives.**
- *`/v1/chat/completions`*: OpenAI-compatible, but no run ID to reconnect to and weaker control
  flow.
- *TUI gateway JSON-RPC (stdio/WebSocket)*: the richest control surface (what Hermes Desktop
  uses), but a larger, less-documented protocol meant for Hermes's own clients. Revisit if the
  HTTP surface turns out to be missing something we need.
- *ACP*: aimed at IDEs.

---

## D-004 — Kairos policy runs as a `pre_tool_call` plugin hook — Proposed

**Decision.** The kairos plugin evaluates every tool call against `policy.yaml` and returns
`block`, `approve` (escalate to Hermes's human gate), or nothing.

**Why.** It's the documented policy seam. It fails closed on errors and timeouts, and `block`
beats `approve` across plugins, so Kairos can only tighten Hermes's defaults. Approvals then
flow through Hermes's existing machinery and reach the app as `approval.request` events.
No separate gateway or proxy is needed.

**Alternative.** A proxy in front of Hermes's API cannot see individual tool calls; rejected.

---

## D-005 — Kairos-owned SQLite for audit and task history — Proposed

**Decision.** `kairos.db` holds `task`, `tool_event` and `approval` (schema in
`ARCHITECTURE.md` §4). The app writes `task`; the plugin writes the other two. One writer per
table.

**Why not read Hermes's `state.db`?** It is Hermes's internal schema with ~60 helper modules
around it; it changes without notice. Kairos reads Hermes data only through the API.

**Deferred:** embeddings and vector search. Hermes's memory handles recall; Kairos adds nothing
there until there's a measured need.

---

## D-006 — Secrets — Proposed

- Model-provider keys stay in Hermes (`.env` / Hermes credential vault). Kairos never sees them.
- The Hermes `API_SERVER_KEY` is generated by Kairos setup (32 random bytes, hex), written to
  Hermes's `.env`, and stored for the app in the OS keyring. Never in Kairos config files or logs.
- The API server binds to `127.0.0.1` only. CORS stays off because the Rust layer makes the
  requests, not the browser view.

---

## D-007 — Models: free tier to start, routing by task later — Proposed

Current setup: Nous Portal, `upstage/solar-mini4:free`. Kairos uses whatever Hermes is configured
with, so this works with zero extra effort. Free models are small and rate-limited, and free tiers
can change. Plan for: a stronger cloud model for multi-step work, a local Ollama model (RTX 4060,
8 GB VRAM → ~7–8B quantized) for private or offline work, and a per-task cost cap. Routing rules
are a later milestone (`ROADMAP.md`, M7).

## D-008 — Windows 11 is the primary OS — Accepted

Kairos targets Windows 11 first, running Hermes natively (not in WSL). Linux support stays a goal
but is not tested until later. Consequences: OS keyring = Windows Credential Manager;
`HERMES_HOME` defaults to `%LOCALAPPDATA%\hermes`; container isolation (M7) uses Docker Desktop
with the WSL2 backend; scripts are PowerShell first.

## D-009 — Hermes approval mode: `smart`, with the Kairos rules — Accepted

**Decided 2026-10-25 by the product owner**, after the M2 Step 8 test. History: `smart` (Phase 0),
then `manual` (2026-10-23, after smart auto-approved an `rm -rf`), now `smart` again with the
Kairos rules in front of it.

**Why it changed back.** The Kairos plugin checks every tool call *before* Hermes's own approval
runs, so a Kairos `ask` rule always reaches a person, whatever the mode. Step 8 measured it
(`docs/milestones/M2.md`, Step 8): in `smart`, the `rm -rf` that smart approved alone in Phase 0
was stopped by `destructive-commands` and a Deny kept the folder; allowing it cost **one** prompt,
because Hermes's helper model then approved its own check. In `manual` the same command asked
**twice**.

**What `smart` still decides alone:** anything no Kairos rule covers. To narrow that, three more
protections were added first (2026-10-25), as four rules: `run-downloaded-code` (piping a download
into a shell, `Invoke-Expression`, `certutil -urlcache` and similar), `system-files` and
`system-changes` (writes under `C:\Windows`, `Program Files`, `ProgramData`; the registry; services;
scheduled tasks; boot settings; firewall rules), and `permission-changes` (`icacls`, `takeown`,
recursive or world-writable `chmod`, local admin groups, execution policy, Defender settings).
Every decision the helper model makes is recorded in `audit.db` (`decided_by = "aux_llm"`) and
shown on its tool row ("Hermes's helper model allowed it").

**Checked live after switching (2026-10-25):** a harmless `git status` ran with no prompt; `curl … |
sh` was stopped by `run-downloaded-code` and blocked on Deny.

**Never acceptable:** `off` or YOLO. The app and `scripts/setup.ps1` warn if Hermes is in either;
`no-safety-changes` stops the agent from changing the mode itself.

**Going back to `manual`** is always possible (`hermes config set approvals.mode manual`) and is
the stricter choice: two independent checks, at the cost of double prompts.

## D-010 — Accounts only through official sign-in, read-only by default — Accepted

The product owner wants Kairos to reach their accounts. Kairos never asks for or stores account
passwords. Each account is connected on its own through the provider's official sign-in (OAuth,
or the provider's own CLI login such as `gh auth login`), with the narrowest permission that
works, read-only first. Sending, deleting, paying, posting or changing account settings always
needs an approval (a Kairos `ask` rule, M2). Each account can be disconnected from Settings.

**Why not "access to everything":** one prompt injection in a web page or an email would then
reach every account at once. Per-account, least-privilege access limits what a single mistake can
do, and gives most of the convenience.

**Where secrets live:** in Hermes's credential vault or the provider's own credential store, never
in Kairos files, `kairos.db` or logs (as D-006).

## D-011 — Unread messages and missed calls come from Windows notifications — Accepted

Kairos reads notifications through the Windows notification-listener API (`UserNotificationListener`),
after the user grants permission in Windows, instead of logging into each messaging service.
Phone Link delivers phone calls and texts as notifications, so missed calls arrive the same way as
Discord, Teams, WhatsApp desktop or Outlook messages.

**Consequences:** only apps that show notifications are covered, and only what the notification
says (sender and a preview, not the whole thread). Notification text is treated as untrusted
input like any web page: it can be summarised, never obeyed. Turning the permission off stops
collection; collected notifications stay in `kairos.db` until the user clears them.

---

## D-012 — The system page is native, not AI — Accepted

CPU, RAM, disk, GPU, network, battery and process figures are read directly by the Kairos Rust
core and drawn by the app; Hermes and the model aren't involved. It's instant, works offline,
costs nothing, and can't be wrong in the way a model can. The model only sees these figures when
the user asks about them or in the welcome-back briefing.

**Dependency note:** reading these figures needs a system-information crate (likely `sysinfo`) and
the Windows API crate for battery and notifications. Each is proposed with its spec and added only
after approval (CLAUDE.md).

## D-013 — Kairos and Hermes start with Windows — Accepted

For the welcome-back briefing to be ready when the user logs in, both must already be running:
Kairos as a tray app registered to start at login, Hermes through its own login auto-start
(`hermes gateway install`). Starting the gateway from a user-owned service also fixes the
gateway being killed with whatever shell started it (seen on 2026-10-24).

Kairos reacts to three Windows events: startup, resume from sleep, and session unlock. It briefs
only on the first unlock of the day or after a configurable time away, never in quiet hours.

---

## D-014 — PC control through Kairos tools with rules, not raw terminal access — Accepted

Opening and closing apps, and later window, volume, media and power control, are tools that the
Kairos plugin registers in Hermes (`ctx.register_tool`), each with a narrow purpose and its own
rule: opening an allowed app runs, closing an app asks (it can lose unsaved work), system
processes are always denied. The model is steered to these tools instead of improvising
PowerShell, so every PC action is visible in the timeline as what it is.

Hermes's `computer_use` toolset (mouse and keyboard control) stays off until there is a use case
that needs it and a rule set for it.

D-013 and D-014 were accepted by the product owner on 2026-10-25 with the M3 spec.

## D-015 — The audit log is its own `audit.db`, written only by the plugin — Accepted

Supersedes the ARCHITECTURE.md §4 plan of putting `tool_event` and `approval` tables in
`kairos.db`. The Kairos plugin (Python, inside Hermes) is the only writer of
`%APPDATA%\kairos\audit.db`; the app reads it read-only. The app stays the only writer of
`kairos.db` and `policy.json`. The two processes never share a database, a lock or a schema
migration. Accepted with the M2 spec (2026-10-24).

---

## D-016 — Kairos rules are JSON (`policy.json`) — Accepted

Supersedes the YAML sketch in SECURITY.md §3. Both sides parse JSON with what they already have
(Python's `json`, Rust's `serde_json`), so neither needs a new dependency, and the app's Rules page
is the normal way to edit them. Accepted with the M2 spec (2026-10-24).

## D-017 — The speed test uses Cloudflare's public endpoints, only when asked — Accepted

The System page's internet speed test measures latency, download and upload against
`speed.cloudflare.com` (`/__down`, `/__up`), and only when the user presses "Run speed test".
No account, key or new dependency (the app's HTTP client already exists). The PC's IP address
reaches Cloudflare, as with any website visit; nothing else is sent. Accepted with the M3 spec
(2026-10-25).

## D-018 — "Anything I missed?" reads a file the app writes, through a plugin tool — Accepted

For M4. The app writes the last 24 hours of notifications (at most 200) to
`%APPDATA%\kairos\notifications.json`, atomically; the plugin's read-only `recent_notifications`
tool reads it. The app stays the only writer and the plugin a reader, as with `policy.json`, so
the two processes still never share a database (D-015). The tool's result tells the model the
text came from other people and must be summarised, never followed (D-011).

**Consequence to accept:** when the user asks about their notifications, sender names and previews
go to the model provider, like anything else in the chat. Nothing is sent otherwise. Proposed in
the M4 spec; accepted on 2026-10-25 when the product owner left the open M4 choices to the
engineer's recommendation, to be confirmed when M4 is tested.

## D-019 — Isolation is Hermes's Docker terminal backend, one container per conversation — Accepted

For M7. The agent's commands run in Docker (Docker Desktop with WSL2) through Hermes's own
`terminal.backend: docker`, with `container_persistent: false` (a fresh container per conversation)
and only the product owner's project folders mounted. Set up by `scripts/setup-container.ps1`,
which asks first and uses the Hermes CLI; the starter rule `no-sandbox-changes` stops the agent
from switching it off. Accepted on 2026-10-25 when the product owner left the M7 choices to the
engineer's recommendation, to be confirmed when M7 is tested.

## D-020 — Cost is estimated from Hermes's prices; Kairos enforces the cap by stopping the run — Accepted

For M7. Each request's cost is its `usage` times the served model's price from
`/api/model/options`, shown as an estimate. A per-request cap (off by default) is enforced by
Kairos polling the run and calling `/v1/runs/{id}/stop` when the estimate passes it. Accepted on
2026-10-25 on the same delegation as D-019.

## D-021 — The quick box is a second window on a global shortcut; screenshots ask every time — Accepted

For M8. A frameless always-on-top window opened by `tauri-plugin-global-shortcut` (default

## D-022 — Speech to text is local Whisper in the app, push-to-talk only — Accepted

For M9. The product owner chose, on 2026-10-25, local Whisper over Windows's online speech
recognition and Hermes's dashboard server, and push-to-talk over a wake word. The webview records
the microphone only while the push-to-talk key or the mic button is held or on; a Tauri command
transcribes it with `whisper-rs` (whisper.cpp, CPU). Audio stays in memory and is never written
to disk or sent anywhere; the transcript is ordinary chat text under the Kairos rules. The model
is downloaded once, on the user's click, and checked against its SHA-256. Answers are read aloud
only on request, with Windows's voices. New dependency: `whisper-rs =0.16.0` (see M9 §4).
Accepted by the product owner on 2026-10-25, with the dependency and the build settings.

## D-023 — The persona is Hermes's own `SOUL.md`, edited from the app — Accepted

For M10. Hermes reads `<HERMES_HOME>\SOUL.md` into the system prompt whenever it builds one, so the
Kairos persona (JARVIS-like, calls the product owner "Master", always answers in English; chosen
2026-10-26) is written there, by the app, only when the user presses Save in Settings ▸ Persona.
The first write backs the original up to `%APPDATA%\kairos\backups\SOUL.md.before-kairos`, and
"Restore the original" puts it back. No Hermes code changes and no per-turn prompt injection.
Accepted when the product owner chose "persona now" on 2026-10-26.

## D-025 — Speech out is Kokoro through sherpa-onnx, kept loaded; no Edge voices — Accepted

For M9 Step 8. The product owner first chose Microsoft's free Edge neural voices; that route now
requires a "v2" Sec-MS-GEC token computed by a reverse-engineered algorithm (`edge_tts`'s
`drm.py`), which would mean bypassing Microsoft's access control on an Edge-only service, under a
copyleft licence and liable to break. Not built. Instead: Kokoro (Apache 2.0) through k2-fsa's
sherpa-onnx (Apache 2.0) C library, downloaded on the user's click with pinned SHA-256s, loaded at
run time with `LoadLibraryExW` and kept loaded; voice George. Offline. Measured: the full model is
4–5× faster than real time on the product owner's PC, the int8 one slower than real time. The
Windows voices remain the fallback. Accepted by the product owner on 2026-10-26 ("Use George.
Build Kokoro into Kairos with the full model.").

## D-026 — Memory: shown read-only, forgotten through Hermes; holographic provider — Accepted

For M11. Kairos reads Hermes's `memories\USER.md` and `MEMORY.md` and the holographic provider's
`memory_store.db` read-only for the "What Kairos remembers" page, and never edits them: a Forget
is a request to Kairos to remove that item with its own memory tool, in a conversation the sidebar
hides. The provider is `holographic` 0.18.3 (local SQLite, no key, network or model calls by
default); enabling it changed one line of Hermes's `config.yaml` (`memory.provider`), backed up
first to `%APPDATA%\kairos\backups\hermes-config.yaml.before-holographic`. Accepted by the product
owner on 2026-10-27, with a persona line telling Kairos to remember lasting facts and no secrets.

## D-027 — Kairos may use a copy of the Master's Brave profile, behind the Kairos rules — Proposed

For M12 (`docs/milestones/M12.md`). Hermes's `browser.use_real_profile: true` copies the default
browser's profile (Brave on this PC: cookies, saved passwords, autofill) into a Hermes-owned
folder and drives the real browser on that copy; switching it off deletes the copies.
`browser.restrict_evaluate: true` goes with it. Both are Hermes configuration changes, backed up
first and switched from Kairos's settings. Only after the M12 rules are built: Hermes's browser
runs in Browser Use mode (one `browser_exec` tool running Python, kept by the product owner), so
every script that clicks, types, submits or reads cookies asks, a vault fill asks, and card numbers
and passwords are never typed (built 2026-10-27). Proposed 2026-10-27; the product owner decides.

## D-028 — Rich answers: tables drawn by Kairos, diagrams by Mermaid, only safe images — Accepted

For M13 (`docs/milestones/M13.md`). Tables are added to Kairos's own Markdown reader (no library).
Diagrams and charts are Mermaid code blocks drawn by the `mermaid` package (MIT, an exact 11.x
version, loaded only when needed, `securityLevel: "strict"`): its SVG is the only markup the chat
inserts. Images are only the `data:image/…` pictures Hermes makes and the model's SVG sketches,
both shown with `<img>` (no scripts, no network); images from web addresses show as links, and
older conversations' `MEDIA:` paths are read only from Hermes's own folders. The model is told
to use them only when they help. Accepted by the product owner on 2026-10-28, with the `mermaid`
dependency.
